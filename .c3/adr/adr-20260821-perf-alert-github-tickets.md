# perf-alert-github-tickets

## Goal

Make a fleet performance regression open its own GitHub issue. Kanna already exports OTel traces and metrics from every install to the shared otel-lgtm collector, but nothing watches that data: the Grafana instance carries zero alert rules and zero contact points, so a regression is found only when a human notices slowness. This decision adds the two performance metrics the fleet does not yet emit (`kanna.turn.duration_ms`, `kanna.subagent.run.duration_ms`), a version-controlled alert-rule set applied to Grafana, and a repository-dispatch path that files a deduplicated, self-closing issue labelled `performance` + `agent-fix` — carrying the firing query, the affected hosts, and the code hints an agent needs to start fixing it.

## Context

Ten installs report to `kanna-otel.lowbit.link` today. What they report is not yet enough to alert on, and nothing is listening.

Measured on the live collector while authoring this decision:

- `kanna_process_rss_bytes` peaked at 2.29 GB, 2.09 GB, 1.96 GB, 1.49 GB and 1.41 GB across five installs in 24 hours. pm2 clamps `max_memory_restart` at 2 GiB, and a breach restarts the server, cancelling in-flight turns and writing an `interrupted` entry indistinguishable from a user Stop.
- `kanna.turn.start` — the only turn span — has a p95 of 0.03–0.47 ms, because it wraps the spawn step and not the turn. There is no usable latency metric at all.
- `kanna_subagent_run_finished_total` reports with its `outcome` label, but at 7-day volumes of 4 completed / 1 failed on a single install: a naive ratio alert would call one failure a 20% failure rate.
- Spanmetrics generated by the collector (`traces_spanmetrics_latency_bucket`) carry only `service`, `span_name` and `status_code` — no `service.version` — so they cannot attribute a regression to a release. Kanna's own OTLP metrics do carry `service_version`.

`adr-20260814-otel-observability` left an explicit governance question open: whether sustained growth of this concern — more spans, more exporters, a dashboard — earns a dedicated component fact. It also recorded that no component owns `observability.ts` or `otel.adapter.ts`, which is why `c3x lookup src/server/otel.adapter.ts` answers "no component mapping found". This decision is that growth, and closes the question.

## Decision

**Emit the missing metrics at the choke points that already exist.** `kanna.turn.duration_ms` is recorded from the `EventStore.onTurnTerminal` observer — the single point every provider terminal path funnels through — enriched from `activeTurns.get(chatId)`, exactly the lookup the cron-outcome consumer already performs there under the invariant that a turn is deleted from the map only after its terminal record persists. That required one new field, `ActiveTurn.startedAt`, carried over from the `StartingTurn` so the measurement includes spawn cost — the latency a user actually waits. `kanna.subagent.run.duration_ms` is recorded beside the existing `kanna.subagent.run.finished` counter, inside the span that already wraps the whole run. Rejected: widening `onTurnTerminal`'s signature (ripples through 24 call sites to serve one observer), recording at each runner terminal site (four sites, guaranteed to drift), and computing it in the reducer, which already derives `lastTurnDurationMs` but has no provider or model and must stay a pure fold.

**Register explicit histogram buckets.** OTel's default explicit boundaries stop at 10 s. A Kanna turn runs seconds to tens of minutes, so under the defaults every observation lands in the `+Inf` bucket and `histogram_quantile` returns nothing usable. `DURATION_BUCKETS_MS` spans 1 s – 30 min and the adapter registers a view over it.

**Alert rules are code, and Grafana holds no logic.** `src/ops/alerting/rules.ts` is a flat spec table — query, threshold, and the context the ticket renders — over a builder that hides Grafana's rule model (refIds, expression nodes, evaluator params). Rules query at instance level so a ticket can name every affected host, while the notification policy groups by `alertname` + `service_version`, so ten breaching installs are one ticket rather than ten. That grouping is chosen because a code fix targets a release, not a laptop.

**The transport needs no relay service.** Grafana 13's webhook contact point supports a custom payload template plus bearer auth and extra headers, which is exactly what GitHub's repository-dispatch endpoint requires. Every interpolation goes through `printf "%q"` so a label containing punctuation cannot produce invalid JSON, and the alert's fields nest under one `alert` key to stay inside GitHub's 10-property `client_payload` limit.

**Two rules arm now; two wait for a baseline.** Memory pressure and subagent failure rate run against data that already exists. The two latency rules are applied *paused*, with a `baselineNote` recording what must be measured first — a threshold guessed before `kanna.turn.duration_ms` has any history is not an alert, it is noise. Arming is one flag plus a re-apply.

**A dedicated component owns the concern.** This creates c3-234 (observability) under c3-2, owning the facade, the adapter, the config resolver and the alerting surface, and closing the question `adr-20260814-otel-observability` deferred.

## Alternatives Considered

| Alternative | Rejected because |
| --- | --- |
| Alert on collector spanmetrics instead of adding metrics | traces_spanmetrics_* carries no service_version dimension, so a regression could not be attributed to a release; and the only turn span measures 0.03–0.47 ms because it wraps the spawn, not the turn |
| Post straight to the GitHub issues API from Grafana | No way to dedupe, throttle, or close: every notification would open a new issue. The dispatch → workflow hop is what buys a read-then-decide step |
| Relay service on Dokploy to translate alerts | A whole deployed service to reshape one JSON body that Grafana's own payload template can already produce |
| Hand-write the Grafana rule JSON | The rule model is verbose enough per rule that thresholds and queries drift apart; a spec table plus a builder makes the threshold reviewable in one place |
| Set latency thresholds now from the spanmetrics p95 | Those p95s measure the spawn step, not a turn. A threshold derived from them would be wrong by three orders of magnitude |
| Trigger an auto-fix agent on the label | Out of scope by explicit choice: it needs an unattended API-key secret in the repo, and the ticket quality has to be trusted first |

| A service_version-grouped rule silently ignores installs older than 1.38.0, which report no version label at all | Queries never require the label; those instances group under an unversioned bucket, and alertMarker renders it as @unversioned | perf-issue.test.ts "an install too old to report a version still groups deterministically" |
| The Grafana notification-policy endpoint is a whole-tree PUT on a shared instance, so applying could delete routes this repo does not own | mergePerfRoute preserves the existing tree and owns exactly one route, keyed by contact-point name; re-applying replaces its own route rather than stacking copies | webhook-payload.test.ts "preserves the default receiver and unrelated routes" and "re-applying replaces its own route rather than stacking copies" |
